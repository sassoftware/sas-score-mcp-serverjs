What is in the ui folder, and why

The ui folder holds the small web page that VS Code shows next to a tool result. It is plain JavaScript and CSS, bundled into one HTML file. This guide covers each file, how the pieces connect, and the reasons behind the main design choices.

The files and what each one does

Four source files, one build config, and one generated output. Only the source files are edited by hand.

ui/index.htmlstatic shell
sourceAn empty page with three elements
It holds #main, a #status line ("Waiting for results...") and an empty #content div, then loads viewer.js. Why: the page never knows what it will show until a result arrives, so everything visible is created by script. That keeps one HTML file able to show every tool.
ui/src/viewer.jsabout 270 lines
sourceThe whole application
It connects to the host, receives the tool result, picks a renderer from viewHint, and handles the Previous/Next buttons, row selection and the Expand button. Why one file: there is a single screen and no state beyond the last result, so a framework would add size and a build step without helping.
ui/src/global.cssabout 100 lines
sourceFallback theme variables
It defines the host style variables (--color-text-primary, --font-sans, spacing and heading sizes) with light-dark() defaults. Why: the host overrides these at runtime with its own colors and fonts, so the view matches VS Code. The defaults keep it readable if the host sends nothing.
ui/src/styles.cssabout 100 lines
sourceLayout for our own views
Table borders and striping, sub-tables, the selectable list, the scroll box, and the Previous/Next and Expand buttons. Why separate from global.css: global.css comes from the MCP Apps template and tracks the host. styles.css is ours and is the only file that normally changes.
vite.config.jsrepo root, not in ui/
buildBundles everything into one file
Vite with vite-plugin-singlefile reads ui/index.html and inlines the script and both stylesheets. Why: the server hands the view to the host as one string, and the sandboxed iframe has no server to fetch extra files from.
dist/ui/index.htmlgenerated, about 237 KB
outputThe file the server serves
createMcpServer.js reads it once and returns it for ui://sasmcp/view.html. Most of the size is the MCP Apps client library bundled into the script. Rebuild with npm run build:ui after any change in ui/.

What viewer.js does while it runs

The script is driven by three kinds of events. Everything else is a helper called from one of them.

1. When the page loads

  1. Create the App object. It talks to the host over postMessage.
  2. Build the Previous/Next bar and the Expand button, both hidden. They appear only when the data or the host allows them.
  3. Register every handler (ontoolresult, onhostcontextchanged, onteardown, onerror).
  4. Call app.connect(), then apply the host context. Theme, fonts, safe-area insets, and the box height.

2. When a tool result arrives

  1. showResult(structuredContent) stores the paging info and shows or hides the pager.
  2. If there are columns and rows, render() reads viewHint and calls the matching renderer.
  3. If the data has another shape, show it as raw JSON.
  4. If there is nothing, show "No structured data in tool result."

3. When the user acts

  1. Previous / Next: sendPrompt(paging.nextPrompt) posts the text to the chat.
  2. Row select (singlelist): replace #SELECTION in nextToolPrompt with the row value, then send it.
  3. Expand: requestDisplayMode switches fullscreen or inline, and the box is resized.
  4. Buttons are disabled while a request is pending. The next result re-enables them.

One view, several layouts

The tool decides what to show by setting viewHint. The view has no knowledge of individual tools, so adding a tool does not mean changing the view.

Design decisions

Each of these has a cost. The notes say what was chosen, why, and what was passed over.

Security

Build the page with textContent, never innerHTML

Why: table values come from SAS data and can contain anything, including markup. The helper el() only ever sets text, so a cell holding <script> is shown as text.

Passed over: template strings with innerHTML. They are shorter to write and unsafe with untrusted data.

Interaction

Buttons send prompts instead of calling the tool

Why: app.sendMessage puts the request in the chat, so the model sees it and the skills that guide the flow still apply.

Passed over: app.callServerTool. It updates the table in place and is faster, but the model never sees the new page.

// the prompt text comes from the tool, not the view
paging: { nextPrompt: 'read the next 20 rows', ... }
Layout

Size the scroll box in pixels, not vh

Why: the host sizes the iframe to fit its content. A box set to a percentage of the viewport height feeds back on itself and collapses. The view reads the host's container size instead and sets one CSS variable, --box-h.

Theming

Use the host's style variables, with fallbacks

Why: the view should look like part of VS Code in light, dark and custom themes. The host sends its variables, applyHostStyleVariables sets them, and global.css covers the case where it sends none.

Passed over: fixed colors of our own. The light-blue table header and the translucent row stripes are the exception, chosen to read on both themes.

Reliability

Register every handler before connect()

Why: the host can send the tool result right after the connection opens. A handler set later could miss it and leave the view on "Waiting for results...".

Build

One bundled file and no framework

Why: the sandbox allows no extra requests for the view, so everything is inlined. With about 270 lines of script, plain DOM calls are easier to read than a framework and keep the file small.

Cost: each new layout is a function that builds elements by hand. If the views grow much more complex, that is the point to reconsider.

Fallback

Show something for every result

Why: a tool can return a shape the view does not know yet. Unknown viewHint values and plain objects render as JSON, and an empty result shows a message, so the user never sees a blank frame.

Adding a new layout

The usual change is a new viewHint. Four steps, all inside ui/ except the tool.

  1. Write the renderer in viewer.jsA function that takes the structured result and returns a DOM element, built with el().
  2. Add it to render()One more branch on viewer === '...', before the renderRaw fallback.
  3. Style it in styles.cssUse the host variables with a fallback, such as var(--color-border-primary, #ccc).
  4. Rebuild and reloadRun npm run build:ui, then reload the VS Code window or restart the server so the host picks up the change.
